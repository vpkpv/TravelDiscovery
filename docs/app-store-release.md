# iOS App Store release (Capacitor wrapper)

TravelDiscovery's native iOS shell wraps the existing `web/` React SPA with
[Capacitor](https://capacitorjs.com/) rather than reimplementing it natively. The web app
is unchanged — Capacitor just loads the built `dist/` bundle inside a native iOS app so it
can be distributed through the App Store (and get access to native APIs later, if needed).

This doc covers what's already done in this repo, and exactly what still requires a Mac
with Xcode and a paid Apple Developer account, which cannot be done from a Linux sandbox.

## What's done and automated here

- **Capacitor added to `web/`**: `@capacitor/core`, `@capacitor/ios`, and `@capacitor/cli`
  (dev dependency) are in `web/package.json`.
- **`web/capacitor.config.ts`**: app name `TravelDiscovery`, app id `app.traveldiscoveries.ios`,
  `webDir: dist`. See "Why this app id" below.
- **`web/ios/`**: the generated native Xcode project (checked into the repo — see "Why
  `ios/` is committed" below). Contains the Xcode project/workspace, `AppDelegate.swift`,
  `Info.plist`, storyboards, and the Capacitor Swift Package (`CapApp-SPM/`).
- **App icon**: generated for the iOS asset catalog from the existing PWA icon
  (`web/public/icon-512.png`, the same gradient pin mark already used for the web
  manifest) using `@capacitor/assets`. It produced a single 1024×1024, no-alpha
  `AppIcon-512@2x.png` in `web/ios/App/App/Assets.xcassets/AppIcon.appiconset/`, which is
  the modern single-size format Xcode expects — no manual per-size icon slicing needed.
  Launch screen images were generated the same way as a side effect (`Splash.imageset/`).
  The source logo lives at `web/assets/logo.png` (a copy of `icon-512.png`) so icons can
  be regenerated with `npm run cap:assets`.
  - Caveat: the source PWA icons top out at 512×512, so the 1024×1024 App Store icon is
    upscaled 2x. Because the artwork is a simple gradient + line glyph (not fine detail or
    text), the upscale is visually clean (checked by hand). If a sharper source ever
    exists, drop a 1024×1024+ `web/assets/logo.png` and rerun `npm run cap:assets`.
- **`npx cap sync ios`** runs clean (verified in this sandbox) — it copies the web build
  into the native project and updates the Capacitor Swift Package. `npm run build` (plain
  Vite build, no Capacitor involved) also succeeds standalone.
- **`npm run cap:ios`** script (`vite build && npx cap sync ios`): the repeatable one-liner
  to rebuild the web bundle and refresh the native project after any `web/src` change.
- **`npm run cap:assets`** script: regenerates the iOS icon/launch-screen set from
  `web/assets/logo.png` if the source art ever changes.

None of this touched `api/auth.py`, `api/approve_users.py`, `api/spotify.py`, or any
sign-in UI in `web/src` — see "Access control" below.

### Why this app id

`app.traveldiscoveries.ios` — reverse-DNS of the real custom domain
(`traveldiscoveries.app`), with an `.ios` suffix to keep the bundle id distinct from a
possible future Android application id (which would conventionally be
`app.traveldiscoveries.android` or similar) under the same reverse-domain root. This is
a judgment call, not something pulled from existing project config (no bundle/app id was
defined anywhere in the repo before this change) — it's easy to change later in
`web/capacitor.config.ts` and in Xcode's "Bundle Identifier" field, but changing it *after*
the app has a real App Store Connect record is disruptive, so it's worth the team
confirming it (or picking a shorter id like `app.traveldiscoveries.app`) before first
submission.

### Why `ios/` is committed

Capacitor's convention is to check the generated native project into the repo (it holds
project-specific native config — bundle id, entitlements, signing settings — that isn't
reproducible purely from `npx cap add ios`, and teams typically hand-edit it in Xcode).
`web/ios/.gitignore` (generated by Capacitor, left as-is) already excludes the
regenerable/environment-specific parts: build output, CocoaPods' `Pods/`, derived data,
Xcode user state, the copied web asset bundle (`App/App/public`, refreshed by every
`cap sync`), and the generated `capacitor.config.json`. Neither `web/.gitignore` nor the
repo root `.gitignore` excludes `ios/`, so nothing needed to change there.

### Access control — unchanged

Sign-in inside the native app goes through the exact same Firebase auth + manual
Firestore-approval flow as the web app today (`api/auth.py`, `api/approve_users.py`,
`web/src` sign-in UI) — none of that was touched. Per this repo's `CLAUDE.md`, that's an
intentional closed-pilot design, not a gap to fix, and wrapping the app natively doesn't
change it: an unapproved user hits the same gate inside the iOS app that they'd hit on the
web.

## What still requires a Mac + Xcode + a paid Apple Developer account

Everything below needs real Apple tooling this sandbox does not have:

1. **Open the generated project.** `open web/ios/App/App.xcworkspace` (not the `.xcodeproj`
   — Capacitor projects use `CapApp-SPM`/CocoaPods-style workspace setup once a Mac runs
   `pod install` or resolves the Swift Package; the `.xcodeproj` alone may be missing
   dependency wiring until Xcode resolves the Swift Package on first open).
2. **Apple Developer account + code signing.** Enroll in the Apple Developer Program
   ($99/yr), create an App ID matching `app.traveldiscoveries.ios` (or whatever id the team
   confirms) in the developer portal, and set up a signing certificate + provisioning
   profile — either via Xcode's "Automatically manage signing" (simplest) or manually.
3. **Capability/entitlement configuration in Xcode**, e.g.:
   - Push notifications, if ever added (not currently used).
   - Associated domains / universal links, if deep-linking from `traveldiscoveries.app`
     is wanted (e.g. shareable trip pages opening the app).
   - Any permission usage strings (`NSLocationWhenInUseUsageDescription`, etc.) only if a
     future native plugin needs them — the current wrapper doesn't call any native APIs
     beyond what Capacitor's core needs.
4. **App Store icon/screenshots for the *listing*** (distinct from the in-app icon already
   generated here): App Store Connect requires marketing screenshots per device size
   (6.9", 6.5", iPad if supporting iPad, etc.) and optionally an App Preview video — these
   have to be captured from the app running on a simulator or device, which needs Xcode.
5. **TestFlight.** Archive a build in Xcode (Product → Archive), upload to App Store
   Connect, and distribute to internal/external testers. Given the closed-pilot access
   model, internal TestFlight testers would still need to be separately approved
   Firestore users to get past sign-in — TestFlight distribution and the app's own access
   control are two independent gates.
6. **App Store Connect submission.** Create the app record, fill in listing metadata
   (description, keywords, privacy nutrition label — relevant here given Spotify +
   Google sign-in + location data — support URL, marketing URL), submit the archived build
   for review, and respond to any App Review feedback.
7. **CocoaPods/Swift Package resolution.** First build on a Mac will need `pod install`
   (if any Capacitor plugin needs CocoaPods) or Xcode resolving `CapApp-SPM` via Swift
   Package Manager — this sandbox could not install or run CocoaPods since it has no
   Ruby/CocoaPods/Xcode toolchain, so this is unverified beyond `npx cap sync ios`
   succeeding at the Node/Capacitor layer.

None of step 1-7 can be faked or partially done without macOS; this doc stops at the
handoff point where a Mac takes over.
